## 3. 最小模型与唯一权威

下面是本次应实现的领域职责与数据关系，不是已经存在的 ORM。物理表只随真实命令和消费者一并加入；不能先建空模型然后报完成。

| 概念 | 必须保存的内容 | 唯一权威与复用 |
| --- | --- | --- |
| FinancialAccount / PaymentInstrument | public_id、归属主体、个人或明确共享范围、币种、现金/银行/余额/信用类型、名称、归档状态、版本 | 资金账户同时承担支付工具角色，不为同一银行卡建两套金额真相；支付宝通知来源仍是渠道，不能默认代表支付宝余额。 |
| CreditFacility | 对应信用资金账户、授信关系/提供方、关联 Debt、可选账单日/还款日与额度信息的来源及日期 | 一个授信关系对应一个 Debt 义务聚合。多次消费进入同一关系；余额由事实计算，Facility 不再保存可写余额。 |
| CreditDraw | 原 Expense/public_id 与事实版本、资金组成编号、Facility/Debt、实际使用金额/币种、时间、原证据和更正关系 | 真实新增信用使用事实；不改冻结本金、不伪装 DebtAdjustment。已产生息费若信用承担，关联独立费用 Expense，并明确其费用性质。 |
| Expense funding | 原消费的现金/信用资金组成、实际付款主体、结算金额、不同币种时的明确换算、未知部分 | 关联同次消费的 CreditDraw 或账户资金变动。只汇总资金组成，不再复制消费统计。支持混合付款，不能要求全单只能一种资金来源。 |
| InstallmentAgreement | 合约来源、明确确认、绑定购买/账单或信用义务、覆盖本金、版本；逐期本金/利息/费用/到期日 | 分期是合约与计划。已发生本金仍由 Debt/CreditDraw 承担；排期不新增购买或再次增加本金。不能由 debt_kind 推断。 |
| Repayment settlement / allocation | 一次实际付款总额、来源账户、结算币种、各目标义务、各期及本金/已产生利息/费用组成、证据、稳定回执 | 复用 Repayment 作为目标义务的实际偿还事实；付款整体及分配是同一命令，现金只扣一次。费用首次发生才产生费用 Expense。 |
| Refund destination / allocation | 既有 ExpenseOffsetFact、实际抵扣的信用义务、退入资金账户或留作溢缴款、各金额 | 消费退回仍只由 OffsetFact 计数；去向关联只改变相应负债/资金，禁止重复生成退款消费。 |
| Account movement | 实际到账/付款/转账/贷款/期初确认或余额核对事实、金额/币种、日期、原事实引用、修正历史 | 余额由期初确认与后续有效变动计算；转账两边同事务。重建投影不生成新经济事实。 |

资金事实与财务事实通过一个稳定经济事件标识关联。它是来源/组成关系，不是新的通用工作流引擎或第二套幂等服务。继续复用 `ApiIdempotencyKey`、既有 OCC、Financial Facts 和 Relationships 命令边界。

CreditFacility 复用 Debt 的追加事实、锁、权限和回执；须扩展实际 fold 输入，包括新增信用使用、费用义务、退回和实际偿还。原冻结本金代表建账时已存在的义务，不是可任意增加的累计消费字段。开户零欠款必须合法；未知初始欠款必须显式标为待核对，不能当零。历史普通 Debt 的原金额口径保留，不静默重新解释。

同一经济事件允许有多个合法组成：购买的 Expense + CreditDraw；还款的 Repayment + 首次费用 Expense + 资金扣款。禁止的是同一原事件被互斥分类后各自确认两套主事实，不是禁止一个真实事件拥有多个正确组成。`PaymentCapture` 的当前单目标回执需要向明确的事实组合衔接，不能成为“一次付款永远只能挂一笔债”的新限制。

## 4. 不变量和消费者可用性

### 确认、来源、恢复

1. 通知、OCR、CSV 和无图手工都进入同一领域语义；无图手工不强制上传附件。识别只建议事件、金额、工具或分期证据，资金账户归属、分期合约和实际还款必须由有权用户确认。
2. 已明确确认的信用消费必须在一个事务中保存消费、资金组成、CreditDraw、历史与稳定回执；任一失败全部回滚，不能先提交 Expense 再用另一次 HTTP 创建债务。
3. 原支付工具未知的普通记账仍可确认消费，但明确显示“付款方式未记录”，不得声称已记欠款/现金。以后补关联时只补资金事实，不再确认第二笔消费。用户已选择信用付款却缺金额/账户时，保存原稿并说明待补项，不能偷偷退化为未关联消费。
4. 更正既有资金来源、金额或类型时，原事实/证据留存，使用原因、原版本和受控补偿；有后来还款、退款或分期时先核对其影响，不能只改外键。
5. 采集身份、经济事件身份、命令幂等键是不同身份。相同通知重放不能重复入账；Alipay 与银行短信的不同原件可由人工关联同一事件，保留两份证据。缺可靠共同身份不按同金额自动合并，图像匹配/学习算法保持等待。
6. 同一通知改分类后旧草稿终结，新主事实接管，旧 key 返回原稳定结果；已确认错误事实通过冲正/撤销与重建更正，不删除历史。已确认错误还款改成消费也必须有正式恢复命令，不能仅支持 pending 草稿。
7. Android 在已有 Room/Outbox 中保留原输入、所有资金组成、账户和账本绑定、原版本与 key；Web 沿现有原稿续办。断网、进程终止、回复丢失使用原提交恢复。已接受但投影刷新失败显示待同步，不能重新付款或再次记账。
8. 服务端权限重新校验，身份切换/撤权不重绑旧意图；读模型不能推进付款、产生利息或确认分期。

### 本金、费用、分期与退款

1. 本金偿还不再次进入消费；利息/手续费按已发生费用记录一次。未来分期息费仍是计划，不能把全部未来费用在建分期时当已消费。已产生未付费用形成费用义务，之后支付只清偿该义务。
2. 还款总额必须能解释为各已确认目标的本金、息费及明确溢缴款之和。不得凭总金额或平台名字猜分配顺序；可基于明确合约给可核对建议。信息不齐的保留在人工核对，不能静默丢掉费用或把未知都当本金。
3. 合约保存逐期明细及来源；等额分期可提供确定性填表辅助，尾差、首期日、每期费用须展示并确认。`floor(累计还款/平均本金)` 不能作为真实“已还期数”。
4. 事后分期只重新安排尚未偿还的明确义务，不新增消费、不再次增加本金；原约定留版本。提前还款、延期、免息/费用减免按实际材料确认，不能硬编码各家平台利率或规则。
5. 退款申请不是已到账退款。消费净额、实际资金去向和分期变化分别有证据；部分退款不得自动终止整份合约，已付手续费不能默认为全部退还。
6. 超过当前欠款的已确认付款/退回须明确记录溢缴款或实际退入的账户，不能负值截零丢钱，也不能当收入。既有普通往来禁止超还的规则不因此全局放宽。

### 原币、现金、账户和家庭

1. 交易原币、信用义务结算币、实际付款账户币、本位币快照分别保存，全部使用既有整数 minor unit 与精度规则。信用义务按约定结算币清偿，本位币金额用于相应日期的统计/估值。
2. 例如欠 USD 100 时折合 CNY 700，支付 USD 100 时折合 CNY 720：原币本金已结清；现金按实际扣款记录，汇兑差异单列说明。不能据 720 > 700 拒绝，也不能把差额当新增购买或手续费。跨币种付款须有实际偿债币金额，报价只作建议。
3. KWD 12,345 minor 仍是 12.345，JPY 123 minor 是 123；未知汇率不造零、不重解释历史快照。新增贷款/资金动作沿既有日期精度、日历版本与原证据语义。
4. 初始余额必须带截止日期和来源；只增加期初资金/义务，不伪造本月收入或消费。对账差异须明确更正原因和事实，不能把最后余额直接覆盖。余额未完整核对时显示已记录范围，不能冒充银行实时余额。
5. 银行转余额、银行卡还信用账户、贷款本金到账/偿还均有不同事件类型；内部转账净现金为零。贷款到账不是工资或消费。收入计划不能充当实际收入到账，实际到账另有资金事实与原计划的可选关联。
6. 个人信用账户默认仅归属人可读写；家庭账本消费的权限不自动扩展到个人额度、全部欠款或其他购买。家庭页仅显示获准的该笔付款说明，账户详情/统计/搜索/导出/缓存也执行相同边界。
7. 家庭消费和个人信用义务可由同一已认证付款人在同一后端事务关联，但分别保留其可见性。别人代付或代还需明确对应关系/双方授权；不能因家庭 Owner 身份直接操作成员个人账户。
8. 资产、负债和净资产按获准范围与同一估值时点聚合；CreditFacility 与其 Debt 只能计一次。未核对余额、未知汇率和未授权账户不能被默认为零。净资产只代表已记录且已授权的范围。

## 5. 用户应当能完成的操作

| 真实入口 | 必须能看见、提交和读回的结果 |
| --- | --- |
| 收件/手工/消费编辑 | 选择或就地新增资金账户；普通现金、信用及混合付款；原交易金额、信用使用额和将改变的结果清楚展示；确认后直接打开来源消费与对应义务。 |
| 往来/信用账户 | 一个花呗关系下看多笔使用、退款、未偿本金、已产生息费、当期应还与明确的核对状态；不把每笔消费挤成互不关联的手工债务。 |
| 还款通知/手工还款 | 选信用关系/目标义务、实际付款账户，核对总额与组成；一次确认后消费不重复、欠款和现金同时正确；原分类错误可恢复。 |
| 分期详情/建立分期 | 普通信用使用可后续纳入分期；明确选择购买或账单、逐期金额/费用/日期；保存后仍只有一次原消费；实际已偿与未来计划分别显示。 |
| 退款/冲正/更正 | 选择实际去向、部分金额和受影响义务；展示分期是否仍有效；保留更正原因、原单与全部历史。 |
| 资金账户/流水 | 期初核对、实际收入、贷款到账、付款、内部转账、账户归档及余额核对；从余额能追溯每笔来源，不自动生成未知流水。 |
| 洞察/预算/消费目标 | 购买与发生费用计消费，本金偿还不重复；退款净额一致；现金收支与消费各有明确标题，不把可自由支配计划当银行余额。 |
| 债务目标/计划 | 新增信用使用会影响剩余义务；实际逐期完成替代平均期数；计划到期不是实际付款，最新欠款/退款使原预测可解释。 |
| 原件/历史/导出/导入 | 原通知/票据引用和资金组成可追溯；下载和恢复含新增事实及版本；未知的新事件不能由旧 CSV 路径当普通消费再导入。 |

Web 与 Android 共用上述命令和解释，复用当前视觉、详情、核对、原稿和 Outbox。Owner/桌面仅负责已有管理和打开产品入口，不建立第三套账务编辑器；iPhone 窄采集继续只提供证据。

## 6. 接入点与迁移边界

- **事实写入**：现有消费确认/更正、`debt_command_service`、还款草稿确认、退款/冲正命令接入同事务资金组成；跨域事务由现有应用命令编排，不由 route 串两个独立提交，也不在业务服务内部提前 commit。
- **读模型**：Debt 当前/历史 fold、`goal_debt_repayment_kpi`、消费 stream/预算/统计、实际账户流水、原件详情、导出须同片列出影响并接通。没有资金来源的历史消费保持“未记录”，不能批量猜花呗或现金。
- **数据与约束**：扩展 source type、外键/唯一性、金额和归属约束，migration 与注册模型一致；引用已有事实的资金组成必须校验币种、金额、版本及权限。新源字段不能绕过现有安全边界。
- **历史债务接管**：人工选择原 Debt、核对截止余额及币种后绑定信用关系；历史本位币 debt 不自动转换为原币信用欠款。导入旧本金的余额承接必须避免再把同期间每笔购买叠加一次；只有已核实的来源关联可消除重复。
- **旧客户端**：新能力显式声明版本/写入能力；新对象不能被旧 `kind`、直接调整本金或平均期数入口写坏。对无法表达新模型的旧写命令给明确升级/核对反馈，保留原意图，不静默忽略字段。
- **回退**：已存在新增事实时不得删除新表降级；停止新增入口仍须能读取、纠错和导出历史。回退程序与数据按既有兼容规则，不借本片开启未授权 Windows 生命周期。
- **退役**：新消费者接管后，信用关系上旧的本金调整伪路径、把 `debt_kind` 当分期合同的入口、平均期数显示和重复资金计算必须退出。普通固定本金往来的有效行为继续保留。

### 当前里程碑内的接线次序

以下是实现依赖顺序，全部属于当前可用性缺口；没有另设 P2，也不以某一片合并作为整项完成。

1. **原事件及纠错**：完成已取得的真实通知链路、pending 分类更正和已确认错误事实的恢复。当前 #609/#611 尚待完整端到端通过；反向的“已确认还款改消费”仍须补正式命令。
2. **信用购买到实际清偿**：资金账户的归属、币种与期初确认，CreditFacility、CreditDraw、消费资金组成，同一次消费确认与原币本金清偿一起接通。Web/Android 必须能建立一个信用关系、连续记录多次使用、从原消费查看信用使用，并确认实际付款账户；不能先开放没有消费关联的空账户页。
3. **费用、分期及退款**：接入逐期合约、付款分配、已发生费用和实际退款去向；更正及提前结清影响可查看。没有明确分配证据的通知继续保留为待核对，不能先按全额本金入账。
4. **完整资金使用**：接通实际收入、贷款到账、自有转账、对账更正、完整度提示和授权范围内的净资产。第二步产生的真实付款已经改变账户资金；本步补齐其余实际资金入口，不重新建立另一套余额。
5. **所有现有消费者收口**：预算/洞察/债务目标/原件/历史/导出与导入、旧客户端写入限制、历史债务接管、权限与离线恢复，均以实际新事实验证。缺失消费者继续阻断本项完成，不仅记台账。

第 2 步必须修改当前真实责任点：消费确认 `expense_review_command_service`；Debt 的新增信用使用、当前/历史 fold 及原币清偿；`debt_service/_query.py` 的列表、详情和参与者权限；Web 与 Android 的原稿、提交及读回。现有 Debt 的本金正数、source_type、source_id、账本可见性约束也需逐项适配信用关系，不能靠创建一笔 0.01 的假欠款开户、绕开约束或让家庭列表读到私人负债。

一个贯穿核对例：同一关系购买 37.90、20.00、5.00，购物支出和新增本金均为 62.90；以后付本金 40.00，另有本次才发生并支付的手续费 1.20，消费累计为 64.10、未偿本金为 22.90、实际现金减少 41.20；随后真实退款 10.00 抵未偿本金，净消费为 54.10、本金为 12.90、该次退款现金变动为零。原通知、三笔消费、费用、还款和退款应各自可追溯；不能只展示相同的最终数字而丢掉它们的关系。

## 7. 最少而有效的验收

复用已有 PostgreSQL 财务/还款/退款测试、Room 原意图恢复、真实通知与财务旅程及最终产物门。下面是不可合并掉的业务结果，**不是一行必须新增一个测试**。不建立第二套模拟产品、数量配额或新的报告平台。

| 合并验证场景 | 真实结果与失败检查 |
| --- | --- |
| 实际 37.90 文案、红包/还款日变形及多金额 | Android 原字段→语义/金额→Room→服务端草稿→人工确认；广告不造钱，不确定仍可核对；普通消费/真实还款/退款提醒不互相抢类型。 |
| 同一信用关系三次购买，再还本金及费用 | 三笔消费只各计一次，累计信用使用可追溯；还款不再算购买；费用只记一次；同键重放不追加事实。 |
| 创建/更正资金组成中途失败、回复丢失、另一端先改 | 所有事实原子回滚或返回原稳定结果，OCC 冲突保留原稿；重试后唯一事实组合。 |
| 普通信用消费后分期、不等额期次、部分还款/提前偿还 | 不新增原购买或本金；逐期实际完成与合约一致；剩余费用按确认材料，不由平均数推断。 |
| 部分退款抵债、还清后退款进银行/溢缴款、撤销错误退款 | 消费净额、负债与现金分别正确，原单/原因/原件留存，分期不被擅自删除。 |
| 已确认错误消费↔还款，pending 误分类恢复 | 原错误事实受控撤销/冲正、新正确事实接管；旧 key/通知重放不能再确认另一主事实；存在后续动作时明确核对。 |
| USD 原币结清汇率变化、KWD/JPY、混合付款 | 原币本金正确结清、现金准确、费用/汇差不冒充购买；未具备结算证据或汇率时原任务可续办。 |
| 期初确认、贷款到账、实际收入、内部转账、净资产 | 期初/贷款不进入收入或消费；转账两边同事务且总额守恒；计划不变实际余额；未知不变零。 |
| 家庭消费由个人信用付款、代还及撤权 | 家庭只见获准消费；其他成员不能经详情/列表/统计/导出读个人资金；离线原意图不换主体。 |
| 原支付多渠道证据、历史债务接管及原件/数据导出 | 已有事实关联不再新建；历史余额与购买不重复；新事实版本/来源/金额可读回，旧导入不误解。 |

完整能力退出须同时有 Web/Android 实际入口、持久化事实和查询结果、原稿/失败恢复、历史迁移及权限证据。只有合同、模型文件、API、部分测试或 CI 全绿均不足。金额、权限、幂等、事务、原件和离线恢复的独立风险继续保留；既有重复检查按已完成的拓扑收敛规则处理。

## 8. 官方语义核对与局限

2026-10-18 只以官方材料核对差异，不把品牌规则写死为所有用户的合同：

- [花呗合同](https://render.alipay.com/p/f/platform/index.html?bizScenario=ch_alipay_chs)：信用使用与分期选择分开，额度冻结也可能尚未实际付款；退款有抵扣和剩余资金去向，具体服务以实际约定为准。由此要求保存明确的事件、合约和去向证据。
- [京东白条退款说明](https://help.jd.com/user/issue/201-625.html)：未偿和已全部偿还时退款处置不同，部分已付服务费不返还。不能统一把退款当取消本金和全部费用。
- [招商银行账单分期条款](https://cc.cmbchina.com/content/loan/zdfqtk.htm)：存在不同还款结构、尾差、提前结清规则，退货并不必然终止已办理分期。小票夹应记录用户实际合约及明细，不自行执行银行计费。
- [GnuCash 信用消费](https://www.gnucash.org/docs/v5/C/gnucash-guide/cc-entercharge1.html)与[还款/退款](https://www.gnucash.org/docs/v5/C/gnucash-guide/cc-enterpay1.html)：分别记录购买、欠款和银行付款有助于避免重复消费。本片借鉴此可解释性，不要求把 Ticketbox 改造成 GnuCash 或另建复式总账。

官方网页不证明用户实际适用费率、账期或本次退款结果；这些由实际证据和人工确认确定。研究没有授权访问银行账户、代用户还款或上传原始通知。
