## Product and command meaning

The user explicitly submits a correction while viewing a confirmed fact under the current logical binding. Viewer remains read-only; the backend remains the final ledger/role authority. The submission is frozen and stored before local acceptance or scheduling can imply it has been kept. A suspended first request, process interruption, subsequent failed GET or screen recreation must not require the user to reconstruct the original correction or create another key.

The complete command includes the target fact and original parent OCC, idempotency key, owner/server/data-generation/ledger binding, reason, scalar changes, original currency and minor amount, and the entire requested items/splits replacements. Omitted collections mean unchanged; an empty collection is an explicit replacement. The existing time/score adapters distinguish absent, value and explicit null. The child request DTOs contain no child OCC: their whole replacements are protected by the reviewed parent OCC. Retry must not recalculate money from current FX/settings or rebuild missing fields from a newer fact.

The controller has adjudicated storage compatibility: new submissions use a versioned, verifiable complete original command. Its typed request retains the original OCC, and the stored row's target/token/binding must agree with that command before sending. Necessary original display context remains available without a successful GET. The existing Room row and its key remain the command's durable publication; no second queue or parallel writer is introduced.

Old normalized payloads contain `expected_row_version: 0`, while their row token may already have been changed by cascade. That lost predecessor cannot be reconstructed from the current server token, clock or timestamps. Such an old intent retains its original stored bytes and key and is visibly marked as requiring review. Unknown or unverifiable formats are not automatically sent, blindly retried or marked DONE. The user may inspect and explicitly discard them; a replacement is a new, explicit submission after reviewing the current fact. The historical reader has no authority to repair the old token or publish the old command as a supported new format.

For a supported original command, transient/unknown-result retry preserves key, full body, original OCC and binding. A conflict requires current-fact review; generic KeepMine or Retry with a fresh token cannot mutate the original command into an overwrite. This must hold at the action owner as well as in the UI. Existing expiry, stale-IN_FLIGHT recovery, target ordering, account/ledger isolation and explicit quarantine/sign-out cleanup retain their current owners. Switching a ledger does not grant permission to send a saved command under another binding.

The backend's existing claim-before-OCC and atomic correction/revision/claim commit remain authoritative. A replay HIT returns the original command's revision together with the current authoritative Expense; it does not promise a byte-identical historical Expense head. Pending local intent must not invent a confirmed revision or replace the authoritative fact with an unconfirmed composite projection.
