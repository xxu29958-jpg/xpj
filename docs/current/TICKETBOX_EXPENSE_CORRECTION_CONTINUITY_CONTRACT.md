## Product and command meaning

The user explicitly submits a correction while viewing a confirmed fact under the current logical binding. Viewer remains read-only; the backend remains the final ledger/role authority. The submission is frozen and stored before local acceptance or scheduling can imply it has been kept. A suspended first request, process interruption, subsequent failed GET or screen recreation must not require the user to reconstruct the original correction or create another key.

The complete command includes the target fact and original parent OCC, idempotency key, owner/server/data-generation/ledger binding, reason, scalar changes, original currency and minor amount, and the entire requested items/splits replacements. Omitted collections mean unchanged; an empty collection is an explicit replacement. The existing time/score adapters distinguish absent, value and explicit null. The child request DTOs contain no child OCC: their whole replacements are protected by the reviewed parent OCC. Retry must not recalculate money from current FX/settings or rebuild missing fields from a newer fact.

The controller has adjudicated storage compatibility: new submissions use a versioned, verifiable complete original command. Its typed request retains the original OCC, and the stored row's target/token/binding must agree with that command before sending. Necessary original display context remains available without a successful GET. The existing Room row and its key remain the command's durable publication; no second queue or parallel writer is introduced.

Old normalized payloads contain `expected_row_version: 0`, while their row token may already have been changed by cascade. That lost predecessor cannot be reconstructed from the current server token, clock or timestamps. Such an old intent retains its original stored bytes and key and is visibly marked as requiring review. Unknown or unverifiable formats are not automatically sent, blindly retried or marked DONE. The user may inspect and explicitly discard them; a replacement is a new, explicit submission after reviewing the current fact. The historical reader has no authority to repair the old token or publish the old command as a supported new format.

For a supported original command, transient/unknown-result retry preserves key, full body, original OCC and binding. A conflict requires current-fact review; generic KeepMine or Retry with a fresh token cannot mutate the original command into an overwrite. This must hold at the action owner as well as in the UI. Existing expiry, stale-IN_FLIGHT recovery, target ordering, account/ledger isolation and explicit quarantine/sign-out cleanup retain their current owners. Switching a ledger does not grant permission to send a saved command under another binding.

The backend's existing claim-before-OCC and atomic correction/revision/claim commit remain authoritative. A replay HIT returns the original command's revision together with the current authoritative Expense; it does not promise a byte-identical historical Expense head. Pending local intent must not invent a confirmed revision or replace the authoritative fact with an unconfirmed composite projection.

## Actual dependency changes since qualified main

The correction repository, correction DTO/domain/mappers, OutboxRepository, PendingMutationDao, AppContainer and backend correction route/service/idempotency owners are unchanged between main `5d460626` and dependency `3aebc234`. Their preimplementation counterexamples therefore still apply.

`CorrectExpenseDispatcher` has changed: PR #377 physically removed its duplicate HTTP classifier and calls `OutboxHttpError.mapOutboxHttpException`. Structured `state_conflict` remains CONFLICT, in-progress is retryable, and unknown/protocol 409 remains visible FAILED. This slice must inherit that implementation and the existing error markers; it must not copy the former generic 409-to-Discarded branch. The shared classifier's other domain decisions are not redefined here.

The two global route calls, factory, ViewModel, sync/drop UI now require and describe Income recovery, including unsupported-format retry refusal. Those are real changed consumers to preserve when adding correction recovery. `RepositoryGraph`'s Income wiring comment and PendingMutationEntity/DispatchResult documentation changed; the correction injection, Room columns, generic cascade/resolve implementation and drain behavior did not. The Income payload and its month semantics are not a correction schema to copy: this correction specifically requires proof of its original parent OCC.

## Test-first counterexamples and retirement

Four tests extend three existing JVM files. They use the real ExpenseRepository/OutboxRepository/OutboxDrainEngine as appropriate, with the established fake DAO and synthetic transport/preceding dispatcher. They introduce no new test framework. Their expected failures below are source-derived predictions until the controller obtains exact-candidate cloud JUnit.

| Test | Concrete counterexample and expected baseline failure |
|---|---|
| `ExpenseCorrectionRepositoryTest.composite correction is persisted before scheduling without waiting for a direct request` | Submit original reason, currency/amount, scalar clear/value changes, one item and one split. The transport signals entry and suspends instead of throwing IOException. The test awaits either local acceptance or that real transport boundary, then requires one saved row and completed local acceptance, with the scheduler observing that already-inserted row and no direct request. Baseline is expected to fail `expected 1 row, actual 0`; unexpected submission errors propagate, and cancellation in finally prevents a hung test. |
| `OutboxDrainEngineTest.successDoesNotRebaseQueuedCompositeCorrection` | An earlier same-target Patch succeeds from V=7 to V=8 while a complete legacy correction waits. Only the earlier row runs. | `OutboxRepositoryTest.compositeCorrectionKeepMineCannotReplaceOriginalCommandIdentity` | A direct generic KeepMine call supplies token 8 for a conflict containing the original token 7/key/body. It must refuse, leave the original visible and not requeue. Baseline returns true and replaces token/key. No fresh-fact review has occurred. |

The last three tests intentionally use the old persisted representation: the newly adjudicated conservative reader cannot justify changing those recorded bytes or treating a fresh token as recovered original proof. Passing these tests will not alone prove recognition or replay of the new supported format.

Production retirement must also migrate the existing direct-success, IOException-fallback and direct-cache-publication assertions in ExpenseCorrectionRepositoryTest and the corresponding Synced/Queued ViewModel tests. Their meaningful assertions about reason/OCC, authoritative revision, binding, refresh failure and frozen-FX/composite coherence must move to the new persistence/dispatch/recovery boundary; they must not be deleted as inconvenient regressions. Existing supported Patch KeepMine/cascade tests remain valid controls. New-command replay needs actual dispatcher/adapter round-trip assertions for the full request and key, not a test that merely finds a field name in JSON.

The completion gate further requires real disk Room close/reopen with the actual repository/adapter graph, the three recovery entrances under failed GET and viewer/changed binding, unsupported/expired action refusal, and a server-committed/lost-response replay that produces one revision. Existing `ExpenseCorrectionDtoContractTest`, `OutboxPayloadCodegenAdapterTest`, `ExpenseFactViewModelCorrectionOutcomeTest`, binding/drain/advice tests and backend `test_expense_corrections.py:155/223/325/357/405` are direct verification consumers. JVM fake-DAO evidence does not substitute for SQLite queries, process death, backend authorization or PostgreSQL transactions.
