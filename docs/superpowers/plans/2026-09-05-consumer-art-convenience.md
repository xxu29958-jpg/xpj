## Third task: interrupted manual entry remains one intent

**Goal:** A household member starts an expense on a phone between other tasks, or in a desktop browser after work. Amount and Save are immediately clear; optional detail stays available. Refreshing, leaving the form or reopening the browser does not silently replace the entered values or their create identity. **Allowed changes:** The existing native manual-entry adapter/template, its scoped browser draft consumer, and the canonical pending/fact landing contexts needed to acknowledge that same creation. **Forbidden surface:** No change to device-scoped idempotency, payload fingerprinting, automatic category behavior, currency/time interpretation, authorization, token renewal, Android Room/Outbox, data-root ownership or held Windows lifecycles. No server-side partial Expense pretending to be an unsubmitted draft. No background publication or claim that an offline browser can load the whole application.

**Recovery design:**

1. A browser draft stores only the six editable field strings, `client_ref`, submission phase and update time. Its scope contains the existing `dataset_id`, `client_generation`, Account public ID, ledger and original Device public ID. Never persist CSRF, cookies, bearer credentials or internal numeric actor IDs in this store.
2. Keep each intent in a separate versioned localStorage entry. An opaque fragment identifies the current draft on refresh; the same manual-entry page lists retained drafts for explicit continuation. Ordinary cross-browser-session persistence is useful here; private-session closure and user-cleared storage cannot be advertised as recoverable. See [localStorage semantics](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage).
3. Acquire the browser's exclusive per-intent [Web Lock](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API) before editing or retiring shared storage. A second tab cannot overwrite that draft and can start a separate fresh form. Never steal the first tab's lock. If storage or locking is unavailable, preserve the native form and show that local retention is unavailable; do not pretend autosave succeeded.
4. Preserve the exact submitted snapshot and original key before native submission. A response-loss retry is the same payload and same Device key, not a new expense. An uncertain submitted snapshot is read-only until the server explicitly rejects it or its canonical Expense is observed. No automatic retry.
5. Only the canonical saved Expense, scoped to the current authenticated Device, can supply the acknowledgement consumed on the pending or confirmed landing page. Query strings and a submit event cannot clear a draft. Ordinary validation rejection retains values and key while permitting correction; changed identity/ledger/role remains blocked by the existing server guard.
6. A changed Account, ledger or dataset generation never receives an automatic restoration. A retained old Device draft in the same Account/ledger remains readable for manual reconciliation, not automatically rebound or retried as a new Device. This task does not claim transparent replay after re-enrollment; the existing fact list and explicit new-entry path remain the decision boundary.
7. Keep amount/currency prominent and optional merchant/category/date/note in native details. Server errors and nonempty restored optional values expose the section. Without JavaScript, all original fields and the native command remain usable; native invalid controls must reveal their section before focus.
